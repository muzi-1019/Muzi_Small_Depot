## 一、项目全局视角

### 1.1 项目是什么？

一句话概括：**让大语言模型（LLM）"读懂"一份 PDF 文档（如招股说明书），然后准确回答关于这份文档的任何问题。**

传统 LLM（如 ChatGPT）的问题是：
- 不知道你的私有文档内容
- 会"胡编乱造"（幻觉）
- 无法引用具体出处

我们的方案 —— **RAG（Retrieval-Augmented Generation，检索增强生成）**：

```
用户提问 → 从文档中检索最相关的片段 → 把片段作为"参考资料"交给 LLM → LLM 基于参考资料生成回答
```

### 1.2 为什么选 RAG？

| 方案 | 优点 | 缺点 |
|------|------|------|
| **纯 LLM** | 简单，无需基础设施 | 不知道私有文档内容，会编造数据 |
| **Fine-tuning（微调）** | 让模型"记住"知识 | 成本极高（GPU+数据），知识过时需重新训练 |
| **RAG（本项目）** | 实时检索最新文档，可溯源，低成本 | 需要向量数据库等额外组件 |

**本项目实测对比**：纯 LLM 关键词准确率仅 **47%**，RAG 达到 **95-100%**。

### 1.3 技术栈全景

## Task 01：基于 PDF 文档的问答系统（基础版）

### 这一步做了什么？

把一份 PDF（武汉兴图新科招股说明书，280 页）变成一个可以问答的知识库。

### 核心流程

```
PDF 文件
  │
  ▼ (1) 文本提取
PyMuPDF 逐页读取
  ├── 文字多（>30字符）→ 直接用
  └── 文字少（扫描件）→ OCR 识别
  │
  ▼ (2) 文本分块
chunk_size=800, overlap=120
  │
  ▼ (3) 向量化
调用 bge-large-zh 模型
"公司注册地在武汉" → [0.12, -0.43, 0.87, ...]（768维向量）
  │
  ▼ (4) 存入向量库
Milvus: {character_id, text, vector, source_file}
  │
  ▼ (5) 检索问答
用户问题 → 向量化 → Milvus COSINE 相似度搜索 → Top-K 片段 → LLM 生成回答
```

### 为什么要分块（Chunking）？

| 不分块 | 分块（本项目） |
|--------|---------------|
| 整页或整文档作为一个向量 | 每 800 字符切一段 |
| 向量过于笼统，丢失细节 | 每段语义集中，检索精准 |
| LLM 上下文塞不下 | 只取最相关的几段 |

**为什么 overlap=120？** 避免一个关键信息刚好被切断——前后两个 chunk 会有 120 字重叠，保证信息完整性。

### 为什么选 COSINE 相似度？

| 度量方式 | 特点 | 适合场景 |
|----------|------|---------|
| 欧氏距离 | 受向量长度影响 | 图像特征 |
| 内积 | 偏向长向量 | 推荐系统 |
| **COSINE（本项目）** | 只看方向不看长度，归一化 | **文本语义匹配** |

### 代码位置

- 文本提取与分块：`app/services/pdf_ingest_service.py` → `_extract_text()` + `_chunk_text()`
- 向量化：`_embed()` 方法，调用 SiliconFlow Embedding API
- 检索：`search_vector()` 方法
- 对话编排：`app/services/chat_service.py` → `send_message()`

## Task 02：检索优化

### 问题：基础版的检索不够准

基础版只用 SHA256 伪向量，实际没有语义理解能力。

### 优化措施

1. **接入真实 Embedding 模型**：从 SHA256 哈希 → `BAAI/bge-large-zh-v1.5`（768 维真语义向量）
2. **Embedding 缓存**：对相同查询不重复调用 API

```python
# 优化前
def _embed(self, text):
    digest = hashlib.sha256(text.encode()).digest()  # 伪向量，没有语义
    return [byte/255*2-1 for byte in digest[:dim]]

# 优化后
def _embed(self, text):
    if text in _embed_cache:                          # 缓存命中，0ms 返回
        return _embed_cache[text]
    response = httpx.post(embedding_api, ...)         # 调用真实模型
    vector = response.json()["data"][0]["embedding"]  # 768维语义向量
    _embed_cache[text] = vector
    return vector
```

### 为什么选 bge-large-zh？

| 模型 | 维度 | 中文效果 | 速度 |
|------|------|---------|------|
| text-embedding-3-small | 1536 | 英文优秀，中文一般 | 快 |
| m3e-base | 768 | 中文不错 | 快 |
| **bge-large-zh-v1.5（本项目）** | 768 | **中文 SOTA** | 中 |
| bge-m3 | 1024 | 多语言 | 慢 |

**结果**：检索准确率从不可用提升至 **≥90%**。

## Task 03：PDF 表格解析及检索优化

### 问题：表格数据解析丢失

PDF 中的表格（如财务数据、股权结构）被提取为乱序文本，关键数字丢失。

### 解决方案

```python
# 使用 PyMuPDF 专门提取表格
tables = page.find_tables()
for table in tables:
    df = table.to_pandas()
    markdown_text = df.to_markdown()  # 转为 Markdown 表格格式
    # "| 项目 | 2018年 | 2017年 |\n| 营业收入 | 19,813 | 15,230 |"
```

### 为什么转 Markdown 格式？

| 方案 | 效果 |
|------|------|
| 直接提取文字 | "营业收入 19813 15230" — 丢失行列关系 |
| JSON 格式 | `{"营业收入": {"2018": 19813}}` — LLM 不擅长 |
| **Markdown 表格（本项目）** | LLM 天然理解 Markdown，保留行列结构 |
| HTML 表格 | 可行但 token 开销大 |

### 代码位置

`app/services/pdf_ingest_service.py` → `_extract_text()` 中的表格提取逻辑。

## Task 05：Query 理解优化（多轮对话）

### 问题：多轮对话中指代关系丢失

```
用户：兴图新科的控股股东是谁？
AI：控股股东是程家明
用户：他持股多少？          ← "他"是谁？直接用这句话去检索，找不到有用信息
```

### 解决方案：Query Rewriting（查询重写）

让 LLM 把当前问题 + 历史上下文，改写为一个独立、完整的新查询：

```
原始问题：他持股多少？
历史上下文：之前讨论了程家明是控股股东
重写结果：程家明在兴图新科的持股比例是多少？ ← 用这个去检索
```

```python
# app/services/llm_service.py → rewrite_query()
def rewrite_query(self, question, memory):
    prompt = f"""根据对话历史，将用户问题改写为独立、完整的查询。
    历史：{memory}
    问题：{question}
    改写："""
    return self._call_llm(prompt)
```

### 为什么不直接拼接历史？

| 方案 | 优点 | 缺点 |
|------|------|------|
| 直接拼接所有历史 | 简单 | Token 开销大，噪声多 |
| 取最近 N 轮 | 简单 | 指代可能在更早的对话中 |
| **Query Rewriting（本项目）** | **精确消解指代** | 需要额外一次 LLM 调用 |

### 配置开关

`settings.query_rewrite_enabled = True` — 可在 `.env` 中关闭以加速首轮对话。

## Task 06：混合检索（向量 + 全文）

### 问题：向量检索的局限

向量检索擅长"语义相似"，但对精确关键词匹配较弱。例如：

```
问题："GB/T28181 标准"
向量检索：可能匹配到"视频传输协议"相关段落（语义相近但不精确）
关键词检索：精确匹配到包含"GB/T28181"的段落 ✓
```

### 三种检索模式

```python
settings.retrieval_mode = "hybrid"  # 可选：vector / keyword / hybrid
```

| 模式 | 原理 | 适合场景 |
|------|------|---------|
| vector | COSINE 语义相似度 | 模糊语义问题（"公司做什么的？"） |
| keyword | **BM25 算法**（TF-IDF 变体） | 精确术语（"GB/T28181"、"19,813万"） |
| **hybrid（本项目默认）** | 两者并行 + 加权融合 | **通用场景** |

### BM25 算法简介

BM25（Best Matching 25）是信息检索领域的经典算法：

```
BM25(q, d) = Σ IDF(qi) × tf(qi,d) × (k1+1) / (tf(qi,d) + k1 × (1-b+b×|d|/avgdl))
```

- **IDF**：词越稀有，权重越高（"兴图新科" > "公司"）
- **TF**：词频越高越相关，但有饱和效应
- **文档长度归一化**：长文档不会因为词多而占优

### 混合检索的融合公式

```
final_score = α × normalize(vector_score) + β × normalize(bm25_score)
```

其中 `α=0.6, β=0.4`（可通过 `.env` 配置 `RAG_HYBRID_VECTOR_WEIGHT`）。

### 代码位置

- BM25 检索：`pdf_ingest_service.py` → `search_keyword()`
- 向量检索：`search_vector()`
- 混合融合：`search_hybrid()`（使用 `ThreadPoolExecutor` 并行执行）
- 路由分发：`search_dispatch()` 根据 `retrieval_mode` 配置自动选择

## Task 07：功能测试及评估

### 为什么需要评估？

不量化就无法改进。我们需要知道：
- 检索到的片段是否相关？（上下文精度）
- 回答是否忠实于检索结果？（忠实度，防幻觉）
- 回答是否切题？（回答相关性）

### 评估指标体系（RAGAS 式）

| 指标 | 含义 | 计算方式 |
|------|------|---------|
| **keyword_accuracy** | 关键词命中率 | ground truth 关键词在回答中出现的比例 |
| **context_precision** | 上下文精度 | 检索到的 K 个片段中，真正相关的比例（LLM 评判） |
| **faithfulness** | 忠实度 | 回答是否完全基于检索结果，无编造（LLM 评判） |
| **answer_relevancy** | 回答相关性 | 回答是否切题（LLM 评判） |

### LLM-as-Judge 方法

传统评估需要人工标注，成本高。我们用 LLM 自身作为评判者：

```python
def eval_faithfulness(question, answer, contexts):
    prompt = f"""
    问题：{question}
    检索片段：{contexts}
    AI 回答：{answer}
    请判断回答中所有事实是否都能在片段中找到依据。
    只输出 0 到 1 之间的数字。
    """
    return float(llm_judge(prompt))
```

### 实测数据（10 题 × 3 模式）

| 指标 | RAG | Graph+RAG | 纯 LLM |
|------|-----|-----------|--------|
| 关键词准确率 | **95%** | **95%** | 47% |
| 上下文精度 | 40% | **45%** | 0% |
| 忠实度 | 54% | 54% | 0% |
| 回答相关性 | 99% | 98% | 89% |

**关键结论**：RAG 的关键词准确率是纯 LLM 的 **2 倍**。

### 代码位置

- 评估脚本：`eval_comprehensive.py`
- 评估报告：`eval_comprehensive_report.md`

## Task 08：Graph+RAG 金融问答（基础版）

### 问题：向量检索找不到"多跳关系"

```
问题："程家明控制的子公司有哪些？"
向量检索：可能找到提到"程家明"的段落 和 提到"子公司"的段落
          但不一定能找到两者的关联关系
```

### 解决方案：知识图谱 + RAG

```
PDF 文本片段
    │
    ▼ LLM 抽取三元组
(程家明) --[控股]--> (兴图新科)
(兴图新科) --[子公司]--> (兴图天建)
(兴图新科) --[子公司]--> (武汉启目)
    │
    ▼ 构建知识图谱
161 个实体节点 + 126 条关系边
    │
    ▼ 查询时
"程家明" → 匹配节点 → BFS 遍历 → 找到所有关联实体
```

### 三元组抽取 Prompt

```python
prompt = """从文本中抽取实体和关系三元组，输出 JSON 数组：
{"source": "实体1", "source_type": "类型", "relation": "关系", "target": "实体2"}
实体类型可选：公司、人物、产品、金额、比例、日期、地点、机构、风险、技术
"""
```

```python
def search_graph(query, max_hops=2):
```

## Task 10：Docker 容器化部署

### 为什么需要 Docker？

| 问题 | Docker 的解决方式 |
|------|-------------------|
| "在我电脑上能跑，你那跑不了" | 容器化封装所有依赖 |
| 手动装 MySQL/Redis/Milvus 太麻烦 | `docker-compose up` 一键启动 |
| 生产环境部署复杂 | 标准化的镜像和编排文件 |

### 架构

```yaml
# docker-compose.yml — 5 个服务
services:
  mysql:      # 用户/会话/角色数据
  redis:      # 短期对话记忆
  milvus:     # 向量检索
  backend:    # FastAPI 后端（多阶段构建：Node编译前端 + Python运行后端）
  frontend:   # Nginx 静态文件 + 反向代理
```

### 多阶段构建 Dockerfile

```dockerfile
# 阶段1：编译前端
FROM node:18-alpine AS frontend-builder
RUN npm ci && npm run build

# 阶段2：运行后端
FROM python:3.12-slim
COPY --from=frontend-builder /build/dist ./frontend/dist
RUN pip install -r requirements.txt
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0"]
```

**好处**：最终镜像不包含 Node.js 和 node_modules（节省 ~500MB）。

### 数据持久化

## Task 11：Embedding 模型微调

### 为什么要微调？

通用 Embedding 模型（bge-large-zh）是在维基百科、新闻等通用语料上训练的。对于金融招股说明书中的专业术语（"募投项目"、"超募资金"、"GB/T28181"），其语义表示可能不够精准。

### 微调方案对比

| 方案 | 训练数据 | 计算成本 | 效果 |
|------|---------|---------|------|
| 全参数微调 | 大量标注对 | GPU × 数小时 | 最好，但易过拟合 |
| **对比学习（本项目方案 A）** | 正例/负例对 | GPU × 分钟级 | 好，数据效率高 |
| **三元组损失（本项目方案 B）** | anchor/pos/neg | GPU × 分钟级 | 好，区分度更强 |
| **LoRA 微调（本项目方案 C）** | 同上 | **显存极小** | 接近全参数，最经济 |

### 训练数据自动构建

```python
# 从 Milvus 知识库自动生成训练数据（无需人工标注！）
# 正例：问题 ↔ 包含答案关键词的片段
# 难负例：问题 ↔ 长度相近但不含关键词的片段（让模型学会区分）

QA_PAIRS = [
    {"query": "公司全称是什么？", "keywords": ["武汉兴图新科电子股份有限公司"]},
    ...
]
positive = find_chunk_containing(keywords)   # 正例
negative = find_similar_length_chunk()       # 难负例
```

### 实际生成数据

- **74 个正例/负例对**
- **60 个三元组**
- 存储路径：`data/finetune/pairs.jsonl` 和 `triplets.jsonl`

### 使用方式

```bash

# 2. 对比学习微调
```

## Task 12：LightRAG 优化

### 传统 Graph RAG 的不足

| 问题 | 说明 |
|------|------|
| 全量重建 | 每次新增文档需要重新处理全部片段 |
| 单层检索 | 只有"实体 → 邻居"一种检索方式 |
| 缺乏全局视角 | 无法回答跨多实体的宏观问题 |

### LightRAG 的三大改进

#### 改进 1：增量更新

```python
# 传统 Graph RAG
def build(chunks):
    graph = {}          # 从零开始
    for chunk in chunks:
        extract(chunk)  # 全部重新抽取

# LightRAG（本项目）
def ingest_chunks(chunks):
    existing = load_existing_graph()       # 加载已有图谱
    ingested_hashes = existing["hashes"]   # 已处理片段的哈希集合
    new_chunks = [c for c in chunks if hash(c) not in ingested_hashes]  # 只处理新片段
    # → 新增 100 个文档不需要重新处理已有的 500 个
```

#### 改进 2：双层检索

```
                    查询
                  /      \
        Local 检索         Global 检索
       (实体邻域)          (社区摘要)
          │                    │
  从匹配实体出发          匹配最相关的社区
  沿边扩展 2 跳          返回社区成员和摘要
          │                    │
          └───── 融合排序 ─────┘
                    │
                最终上下文
```

- **Local**：回答"程家明控制了哪些子公司？"（具体关系）
- **Global**：回答"公司的股权结构是怎样的？"（宏观视角）

#### 改进 3：社区发现

使用连通分量算法自动聚类，将图谱中紧密关联的实体归为"社区"：

```
社区1 (12个实体): 兴图新科, 程家明, 陈爱民, 兴图天建, 武汉启目...
  → 摘要: 兴图新科--[实际控制人]-->程家明; 兴图新科--[子公司]-->兴图天建; ...

社区2 (8个实体): 中泰证券, 发行人, IPO, 保荐, ...
  → 摘要: 中泰证券--[保荐]-->兴图新科; ...
```

### 实际构建结果

| 指标 | 传统 Graph RAG | LightRAG |
|------|---------------|----------|
| 实体数 | 161 | 155 |
| 关系数 | 126 | 136 |
| 社区数 | — | **37** |
| 增量更新 | ✗ | **✓** |
| 双层检索 | ✗ | **✓** |

### 实测对比（8 题）

| 指标 | 传统 RAG | Graph+RAG | LightRAG |
|------|---------|-----------|----------|
| 关键词准确率 | 100% | 100% | **100%** |
| 平均耗时 | 13.6s | 11.5s | **12.3s** |
| 检索耗时 | 2.0s | **0.3s** | **0.3s** |

## Task 13：RAG 性能瓶颈识别与优化

### 方法论：先测量，再优化

> "不测量就优化，等于蒙着眼睛开车。"

### 分阶段计时

对 RAG 问答的 **9 个阶段**分别精确计时（使用 `time.perf_counter()`）：

```python
class Timer:
    def __enter__(self):
        self._start = time.perf_counter()
    def __exit__(self, *args):
        self.elapsed = time.perf_counter() - self._start

with Timer("embedding") as t:
    vector = embed(query)
stages["embedding"] = t.elapsed
```

### 优化前瓶颈分析

| 阶段 | 耗时 | 占比 | 是否瓶颈？ |
|------|------|------|-----------|
| Query Rewrite | 0.00s | 0% | |
| Embedding | 0.77s | 3% | |
| Vector Search | 1.46s | 6% | |
| **Keyword Search (BM25)** | **7.24s** | **28%** | **🔴 瓶颈** |
| **Hybrid Merge** | **7.28s** | **28%** | **🔴 瓶颈** |
| Graph Retrieval | 0.01s | 0% | |
| LightRAG Retrieval | 0.00s | 0% | |
| Context Assembly | 0.00s | 0% | |
| **LLM Generation** | **9.06s** | **35%** | **🔴 瓶颈** |
| **总计** | **25.81s** | | |

**诊断结论**：BM25 每次从 Milvus 拉取 2000 行文档 + 重新分词 = 7.24s；Hybrid 因为串行等待 BM25 = 7.28s。

### 优化措施：BM25 文档缓存

```python
# 优化前：每次查询都从 Milvus 拉 2000 行
def search_keyword(query):
    rows = collection.query(limit=2000)  # 每次拉取 ~7s
    tokenize(rows)                       # 每次分词
    bm25_score(rows, query)

# 优化后：缓存文档列表和分词结果（300秒 TTL）
_bm25_cache = {}

def search_keyword(query):
    cache = _get_bm25_cache(character_id)  # 命中缓存 <1ms
    bm25_score(cache["doc_tokens"], query)  # 直接计算
```

### 优化效果

| 阶段 | 优化前 | 优化后 | 提升 |
|------|--------|--------|------|
| **总平均耗时** | 25.81s | **13.07s** | **↓49%** |
| Keyword Search | 7.24s | **1.52s** | **↓79%** |
| Hybrid Merge | 7.28s | **0.30s** | **↓96%** |
| 检索链路合计 | 16.75s | **3.25s** | **↓81%** |

优化后瓶颈转移至 LLM 生成（占 75%），这是远程 API 的固有延迟，需要部署本地推理服务进一步优化。

### 进一步优化建议

| 瓶颈 | 优化方案 | 预期效果 |
|------|---------|---------|
| LLM 生成 9.81s | 部署本地 vLLM/SGLang 推理服务 | ↓70%（~3s） |
| LLM 生成 | 使用 DeepSeek-V2-Lite 等小模型 | ↓50% |
| Embedding 0.68s | 部署本地 TEI 服务 | ↓80%（~0.1s） |
| Vector Search 0.75s | 创建 IVF_FLAT 索引 | ↓50% |

- 性能分析脚本：`scripts/profile_rag.py`
- 性能报告：`profile_report.md`
- BM25 缓存实现：`pdf_ingest_service.py` → `_get_bm25_cache()`
