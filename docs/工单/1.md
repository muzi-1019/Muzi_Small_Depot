下面这些回答可以结合你的项目现状来讲：你的系统是 **基于 RAG 的角色对话系统**，核心能力包括：

- **多轮对话**
- **Milvus 向量检索**
- **Redis 短期记忆**
- **MySQL 持久化会话**
- **Neo4j 图谱辅助召回**

# 1. 多轮对话：如果上个问题是多实体，怎么判断下一个问题指的是哪个实体？

## 回答思路

多轮对话中，最难的是 **指代消解**。

例如上一轮用户问：

```text
A 公司和 B 公司的营收分别是多少？
```

下一轮问：

```text
它的净利润呢？
```

这里的“它”可能指：

- **A 公司**
- **B 公司**
- **两个公司都要比较**
- **用户表达不清，需要澄清**

**在我的项目里，多轮对话主要依靠两层机制：**

## 第一层：上下文记忆

系统会把最近几轮对话保存到 Redis 中：

```
用户: A 公司和 B 公司的营收分别是多少？
AI: A 公司营收为...，B 公司营收为...
用户: 它的净利润呢？
```

然后在下一次构造 prompt 时，把这些历史上下文一起传给大模型，让模型结合上下文判断“它”指谁。

对应位置：

```text
app/services/memory_service.py
app/services/chat_service.py
app/services/llm_service.py
```

## 第二层：问题改写 query rewrite

系统中有问题改写逻辑，会把用户的简短问题改写成适合检索的完整问题。

例如：

```text
它的净利润呢？
```

如果历史里只有一个实体，系统可以改写成：

```text
A 公司的净利润是多少？
```

如果历史中有多个实体，系统可以改写成：

```
A 公司和 B 公司的净利润分别是多少？
```

## 但是如果仍然无法判断怎么办？

如果上文确实有多个实体，并且用户没有明确指代对象，那么不能强行猜。

更稳妥的方案是：

> **把选择权交给用户。**

例如系统会返回：

```
你想查询哪个对象的净利润？
1. A 公司
2. B 公司
3. 两家公司都查询
```

这样可以避免模型误判。

## 答辩总结说法

可以这样回答：

> 我们系统目前通过 Redis 短期记忆保存最近多轮上下文，并在检索前使用大模型做 query rewrite，把用户的模糊问题改写成完整检索问题。如果上文只有一个明确实体，可以自动补全；如果上文存在多个候选实体，系统不应该强行判断，而是通过澄清问题把候选实体返回给用户选择，这样可以降低多实体指代错误带来的检索偏差。

# 2. 跨页表格合并：翻页的表格怎么判断是同一个表格，并拼接在一起？

## 问题本质

PDF 表格跨页时，通常会出现这种情况：

第一页：

```html
<table>
  <tr><td>项目</td><td>2022</td><td>2023</td></tr>
  <tr><td>营业收入</td><td>...</td><td>...</td></tr>
</table>
```

第二页：

```html
<table>
  <tr><td>净利润</td><td>...</td><td>...</td></tr>
  <tr><td>资产总额</td><td>...</td><td>...</td></tr>
</table>
```

它们在 PDF 里可能被解析成两个独立表格，但语义上其实是同一个表。

## 判断是否为同一张表的方法

可以从几个维度判断：

## 1. 表头相似度

如果下一页表格的列数相同，表头相同或高度相似，说明可能是同一个表格延续。

例如：

```
项目 | 2021 | 2022 | 2023
```

下一页如果仍然是：

```
项目 | 2021 | 2022 | 2023
```

可以判断为同表续接。

## 2. 列数和列宽一致

PDF 表格解析时可以拿到单元格的坐标信息：

```
x0, y0, x1, y1
```

如果两页表格：

- 列数一致
- 每列 x 坐标基本一致
- 表格宽度一致
- 左右边界一致

那么大概率是同一张表。

## 3. 页尾和页首位置关系

如果第一页表格一直延伸到页面底部，而第二页顶部马上出现表格，则说明有跨页可能。

判断条件可以是：

```
第一页表格 bottom 接近页底
第二页表格 top 接近页顶
```

## 4. 是否出现“续表”标识

有些 PDF 会写：

```
续表
表 3-1 续
continued
```

如果检测到这些关键词，也可以判断为同一表格。

## 5. 表格标题一致

如果两页表格上方标题一致，或者第二页没有新标题但结构延续，也可以作为依据。

## 合并方式

解析后可以将表格统一转成结构化格式：

```json
{
  "table_id": "table_001",
  "page_start": 5,
  "page_end": 6,
  "columns": ["项目", "2021", "2022", "2023"],
  "rows": [
    ["营业收入", "...", "...", "..."],
    ["净利润", "...", "...", "..."],
    ["资产总额", "...", "...", "..."]
  ]
}
```

如果是 HTML 结构，则可以拼接：

```html
<table>
  <tr><td>项目</td><td>2021</td><td>2022</td><td>2023</td></tr>
  <tr><td>营业收入</td><td>...</td><td>...</td><td>...</td></tr>
  <tr><td>净利润</td><td>...</td><td>...</td><td>...</td></tr>
</table>
```

## 答辩总结说法

> 跨页表格合并不能只看文本内容，还要结合 PDF 的空间结构。我们会综合判断表头相似度、列数、列宽、单元格坐标、页尾页首位置关系以及“续表”等关键词。如果判断为同一表格，就把后续页的 `<tr>` 行追加到上一页表格中，同时保留 page_start、page_end、source_file 等元数据，方便后续检索和溯源。

# 3. 图像异步：API 图像解析容易堵塞，如何处理？

## 问题本质

图片解析通常比文本解析慢，尤其是调用多模态 API 时，会遇到：

- API 响应慢
- 图片数量多
- 网络不稳定
- 单个请求阻塞整个 PDF 入库流程
- 用户等待时间过长

所以图片解析不适合放在主流程里同步执行。

## 解决思路

采用 **异步解耦架构**。

## 原流程

```
上传 PDF
-> 解析文本
-> 解析表格
-> 调用图像 API
-> 等待图像 API 返回
-> 入库
```

问题是图像 API 卡住时，整个流程都卡住。

## 改进后流程

```
上传 PDF
-> 快速解析文本和表格
-> 抽取图片资源
-> 图片先保存到本地或对象存储
-> 写入图片任务队列
-> 主流程先完成入库
-> 独立图片解析服务异步消费任务
-> 解析完成后回写数据库
```

## 可以用的技术方案

- **Celery + Redis**
- **FastAPI BackgroundTasks**
- **独立 worker 服务**
- **消息队列**
- **任务状态表**

例如状态设计：

```
pending     等待解析
processing  正在解析
success     解析成功
failed      解析失败
```

## 连贯性怎么保证？

图片解析虽然异步，但需要和原文保持关联。

所以每张图片要保存元数据：

```json
{
  "image_id": 1001,
  "source_file": "招股说明书.pdf",
  "page": 35,
  "bbox": [x0, y0, x1, y1],
  "nearby_": "图 3-2 公司组织结构图",
  "caption": "公司组织结构图",
  "status": "pending"
}
```

这样即使图片异步解析，也能知道它来自哪个 PDF、哪一页、附近文本是什么。

## 答辩总结说法

> 图像解析属于高延迟任务，所以不应该阻塞 PDF 主入库流程。我们的思路是先抽取图片并保存路径和上下文元数据，然后把图片解析任务放入队列，由独立 worker 异步调用多模态模型解析。主流程先完成文本和表格入库，图片解析完成后再回写数据库。这样既保证了系统响应速度，也保留了图片与原文页面、标题、上下文之间的连贯关系。

# 4. 项目各阶段不同方案对比，如何突出技术亮点？

这个问题答辩时要从 **为什么选这个方案** 来讲，而不是只讲“我用了什么技术”。

可以按项目演进阶段回答。

------

## 阶段一：直接大模型问答

## 方案

用户问题直接发给大模型。

## 优点

- 实现简单
- 响应自然
- 不需要知识库

## 缺点

- 容易幻觉
- 不能回答私有文档问题
- 无法溯源
- 对专业文档不可靠

## 为什么不用纯 LLM？

因为项目场景是：

> 针对用户上传的 PDF、招股说明书、专业资料进行问答。

这类问题要求：

- 答案准确
- 可追溯来源
- 能引用原文
- 支持私有知识

所以纯 LLM 不够。

------

## 阶段二：基于 RAG 的文本检索问答

## 方案

```
PDF 切分
-> embedding
-> Milvus 向量库
-> 相似度检索
-> LLM 生成
```

## 优点

- 能回答私有文档问题
- 可返回来源片段
- 降低幻觉
- 支持大文档问答

## 缺点

- 对表格、图片、结构关系理解不够
- 对多实体、多跳问题支持有限

## 技术亮点

- 使用 Milvus 做向量检索
- 使用 COSINE 相似度
- 每个角色独立 collection
- 支持 RAG 与纯 LLM 对比

------

## 阶段三：混合检索

## 方案

同时使用：

- 向量语义检索
- 关键词/BM25 检索
- 图谱关系召回

## 优点

- 向量检索适合语义相近问题
- 关键词检索适合精确术语、数字、专有名词
- 图谱适合实体关系查询

## 技术亮点

> 不是只依赖单一向量检索，而是结合语义、关键词和结构化关系，提高专业文档场景下的召回率。

------

## 阶段四：多轮对话增强

## 方案

- MySQL 保存完整历史
- Redis 保存短期上下文
- query rewrite 做指代消解

## 解决的问题

- 用户追问时不用重复背景
- 支持“它”“这个指标”“这家公司”等指代表达
- 多轮问答更自然

------

## 阶段五：表格和图片增强

## 方案

- 表格结构化解析
- 跨页表格合并
- 图片资源抽取
- 多模态模型异步解析图片

## 解决的问题

- 专业 PDF 里很多关键数据在表格中
- 流程图、结构图、组织架构图有信息价值
- 图片 API 慢，需要异步解耦

## 答辩总结说法

> 项目不是一开始就使用复杂方案，而是根据场景逐步演进。纯 LLM 解决通用对话，但不能解决私有文档准确性；RAG 解决私有知识问答，但对表格、图片、多轮指代仍有不足；因此进一步引入混合检索、Redis 多轮记忆、Neo4j 图谱召回、表格结构化和图片异步解析。最终方案是围绕专业文档问答场景，解决准确性、可溯源、多轮理解和多模态信息利用的问题。

------

# 5. 图片资源：不同类型图片如何处理？

图片不能一概而论，需要按价值分类处理。

------

## 第一类：有语义价值的图片

例如：

- 流程图
- 组织结构图
- 架构图
- 业务流程图
- 产品结构图
- 技术路线图

这些图片包含真实信息，应该进入 RAG。

## 处理方式

调用多模态模型识别图片内容，例如：

```
请识别这张流程图中的节点、箭头方向、层级关系，并输出结构化描述。
```

返回结果可以是：

```json
{
  "type": "flowchart",
  "summary": "该图展示了产品生产流程",
  "nodes": ["原材料采购", "生产加工", "质量检测", "成品入库"],
  "edges": [
    ["原材料采购", "生产加工"],
    ["生产加工", "质量检测"],
    ["质量检测", "成品入库"]
  ]
}
```

然后把图片描述文本向量化，进入 Milvus 检索。

------

## 第二类：展示价值图片

例如：

- 公司照片
- 产品图片
- 宣传图
- 封面图
- 装饰性图片

这些图片不一定适合做语义检索，但可以作为展示资源。

## 处理方式

保存图片路径和元数据：

```json
{
  "image_path": "/uploads/images/xxx.png",
  "page": 12,
  "caption": "公司厂区照片",
  "source_file": "招股说明书.pdf"
}
```

当用户搜索相关内容时，如果检索到对应文本片段，可以把图片作为关联资源返回给前端展示或下载。

例如：

```
答案：公司主要产品包括...
相关图片：产品结构图，点击下载
```

------

## 第三类：多模态 RAG 拓展资源

未来可以支持真正的多模态检索：

- 文本查图片
- 图片查文本
- 图片查图片
- 图文联合检索

例如用户上传一张结构图，系统可以检索知识库中相似结构图。

技术上可以使用：

- CLIP embedding
- 多模态 embedding
- 图像向量库
- 图文联合 embedding

## 答辩总结说法

> 图片资源不能简单丢弃，也不能全部都进入文本检索。我们会按图片价值分层处理：流程图、结构图这类有语义价值的图片，调用多模态模型解析成结构化描述后进入 RAG；产品图、照片等展示价值图片，则保存路径和元数据，作为答案关联资源返回；未来还可以拓展到基于 CLIP 或多模态 embedding 的图文联合检索，实现多模态 RAG。

# 6. 问题改写：大模型没办法精确判断时怎么办？

## 回答思路

问题改写 query rewrite 很重要，但不能完全依赖大模型。

例如用户问：

```
它的毛利率是多少？
```

如果上文有多个实体，大模型可能误判。

## 解决方案

当系统检测到多个候选实体时，不直接改写，而是向用户澄清。

例如：

```
你想查询哪个对象的毛利率？
1. A 公司
2. B 公司
3. 两家公司都查询
```

## 技术上怎么实现？

可以在 query rewrite 后增加置信度判断。

## 方法一：让大模型返回结构化结果

```json
{
  "rewritten_query": "A 公司的毛利率是多少？",
  "confidence": 0.62,
  "ambiguous": true,
  "candidates": ["A 公司", "B 公司"]
}
```

如果：

```
ambiguous = true
```

或者：

```
confidence < 0.8
```

就不直接检索，而是让用户选择。

## 方法二：实体抽取 + 候选实体列表

从历史对话中抽取实体：

```
A 公司
B 公司
C 产品
```

如果当前问题出现：

```
它、该公司、这个产品、上述企业
```

同时候选实体数量大于 1，就触发澄清。

## 方法三：前端交互选项

前端展示：

```
你指的是？
[ A 公司 ] [ B 公司 ] [ 两者都要 ]
```

用户点击后，系统再构造明确 query：

```
A 公司的毛利率是多少？
```

## 答辩总结说法

> query rewrite 可以提升多轮检索效果，但不应该把所有判断都交给模型。当存在多个候选实体或模型置信度不足时，系统应该进入澄清流程，把候选实体展示给用户选择。这种 human-in-the-loop 的方式可以显著降低多轮对话中的误检索和误回答。

# 7. 表格检索中的技术、实现思路、方案利弊

表格检索和普通文本检索不同，因为表格有二维结构。

例如：

| 项目     |   2021 |   2022 |   2023 |
| :------- | -----: | -----: | -----: |
| 营业收入 |    1亿 |    2亿 |    3亿 |
| 净利润   | 1000万 | 2000万 | 3000万 |

如果简单把表格转成纯文本，可能会丢失：

- 行列关系
- 表头对应关系
- 单元格含义
- 单位
- 年份
- 指标归属

------

## 方案一：表格转纯文本后向量化

## 做法

把表格转成：

```
表格：主要财务指标
项目：营业收入，2021 年：1 亿，2022 年：2 亿，2023 年：3 亿
项目：净利润，2021 年：1000 万，2022 年：2000 万，2023 年：3000 万
```

然后 embedding 入 Milvus。

## 优点

- 实现简单
- 可以直接复用现有 RAG 流程
- 对自然语言问题友好

## 缺点

- 表格结构损失较多
- 对复杂表头、合并单元格支持弱
- 数字精确查询不稳定

------

## 方案二：结构化表格存储

## 做法

把表格解析成 JSON：

```json
{
  "table_title": "主要财务指标",
  "columns": ["项目", "2021", "2022", "2023"],
  "rows": [
    {
      "项目": "营业收入",
      "2021": "1亿",
      "2022": "2亿",
      "2023": "3亿"
    }
  ]
}
```

检索时可以按字段查询。

## 优点

- 保留行列结构
- 适合精确查询
- 适合做数值比较
- 可解释性强

## 缺点

- 解析复杂
- 对 PDF 表格质量依赖高
- 合并单元格、跨页表格处理难度大

------

## 方案三：表格行级 chunk

## 做法

每一行作为一个 chunk，同时带上表头：

```
表名：主要财务指标
列名：项目、2021、2022、2023
当前行：营业收入、1亿、2亿、3亿
```

## 优点

- 比整表向量化更细粒度
- 能准确定位到某一行
- 适合 RAG 引用来源

## 缺点

- 行与行之间的上下文可能断裂
- 对需要跨行比较的问题支持一般

------

## 方案四：表格整体 + 行级混合索引

## 做法

同时保存：

- **整表摘要 chunk**
- **表格标题 chunk**
- **行级 chunk**
- **单元格级结构化数据**

检索时先召回相关表，再定位具体行/单元格。

## 优点

- 兼顾语义检索和精确定位
- 适合复杂表格问答
- 可以支持比较类问题

## 缺点

- 系统复杂度较高
- 存储成本更高
- 需要更复杂的检索融合策略

------

## 推荐你项目里的最终表述

你的项目可以这样讲：

> 当前系统主要以文本 chunk 和向量检索为主，对于表格内容，会把表格转成带有表头和行列关系的文本描述，再进入 Milvus 检索。后续优化方向是把表格解析成结构化 JSON，并采用整表摘要、行级 chunk、单元格结构化索引的混合方案。这样既可以利用向量检索处理自然语言问题，也可以保留表格的精确行列关系，提升财务指标、年份数据、对比分析类问题的准确性。

# 最后答辩总结模板

你可以在答辩中整体这样总结：

> 本项目的核心目标不是简单做一个聊天机器人，而是面向专业文档、招股说明书、企业资料等复杂知识场景，构建一个可追溯、可多轮交互、支持结构化和非结构化信息的 RAG 问答系统。
>
> 在技术方案上，系统从纯 LLM 问答逐步演进到基于 Milvus 的向量检索，再加入 Redis 多轮记忆、query rewrite、Neo4j 关系召回、PDF 表格结构化处理和图片异步解析。每一步都是针对实际问题设计的：RAG 解决私有知识和幻觉问题，多轮记忆解决上下文连续性问题，表格结构化解决财务数据精确问答问题，图片异步解析解决多模态资源利用和接口阻塞问题。
>
> 对于模型不确定的问题，比如多实体指代，我们不会完全依赖模型猜测，而是通过候选实体澄清把选择权交给用户，保证系统回答的可靠性。未来还可以进一步扩展到多模态 RAG，实现文本、表格、图片、图谱的统一检索和问答。
