# 一、系统整体架构图

这张图描述了**整个系统由哪些"房间"组成，以及房间之间怎么连线**。

## 1. 浏览器（最外层入口）





```
Browser["浏览器 React+Vite"]
```

用户打开网页，就是这个起点。React 是前端框架（负责画页面），Vite 是打包工具（让页面加载更快）。

------

## 2. 前端（FE，运行在 :5173 端口）



 

```
前端 :5173
├── F1 登录注册
├── F2 角色选择
├── F3 聊天界面 SSE
└── F4 知识库管理
```

前端是**用户能看到和点击的部分**，分四个功能页：

- **F1 登录注册**：输入账号密码，换取一个 JWT Token（类似门禁卡），后续所有请求都要带着它。
- **F2 角色选择**：选择要和哪个角色对话（每个角色有独立的知识库和人设）。
- **F3 聊天界面 SSE**：发送消息、看回答的页面。SSE 是「Server-Sent Events」——后端一边生成文字一边推给前端，实现打字机效果，而不是等全部生成完再一次性返回。
- **F4 知识库管理**：上传 PDF 文件，触发知识入库流程。

------

## 3. 后端（BE，运行在 :8000 端口）

后端分三层，从外到里：

### 第一层：API 路由（APIL）

```
/auth      → JWT 鉴权
/chat      → 流式聊天
/characters→ 角色增删改查
/knowledge → 知识管理（上传PDF）
/graph     → 图谱查询
/admin     → 后台管理
```

**路由层只做两件事：接收请求、分发给对应服务。** 每个路径对应一种操作类型，类似一个公司的前台，你说「我要找财务部」它就把你领过去。

### 第二层：核心服务（SVC）

这是真正干活的地方，共 7 个服务：

```
S1 ChatService       — 聊天编排中心（最重要，是总调度）
S2 LLMService        — 调用大模型（DeepSeek）
S3 PDFIngestService  — PDF解析 + 混合检索
S4 MemoryService     — 短期记忆（Redis）
S5 GraphService      — 知识图谱（Neo4j）
S6 LightRAGService   — 图+向量混合检索
S7 ContextService    — 当前天气/IP/时间等环境信息
```

**S1 ChatService 是整个后端的"大脑"**，它调用其他所有服务，把结果组合成一个完整的回答。

### 第三层：基础设施（INFRA）

```
I1 config.py   — 所有配置项（API地址、模型名、参数）
I2 security.py — 密码加密 + JWT 签发/验证
I3 deps.py     — 依赖注入（谁需要数据库连接就给谁）
I4 logging     — 统一日志
```

这层是"地基"，不直接处理业务，负责整个后端能正常运行的基本保障。

------

## 4. 数据存储（DB）

```
MySQL   — 存用户、角色、会话、消息（永久）
Redis   — 存短期记忆/槽位（临时，重启会清）
Milvus  — 存向量 + BM25 索引（知识检索用）
Neo4j   — 存知识图谱（实体关系）
```

四个数据库各司其职：

| 数据库 | 存什么                           | 特点                       |
| :----- | :------------------------------- | :------------------------- |
| MySQL  | 用户账号、角色信息、完整聊天记录 | 关系型，永久可靠           |
| Redis  | 最近 20 轮对话缓存               | 极快，用完即丢             |
| Milvus | PDF 内容的向量 + 分词索引        | 专为相似度搜索设计         |
| Neo4j  | 实体之间的关系（谁控股谁）       | 图数据库，擅长多跳关系查询 |

------

## 5. 外部云服务

```
SiliconFlow API → LLM + Embed + Rerank
```

大模型（DeepSeek）、向量化模型（bge-large-zh）、精排模型（bge-reranker）都通过 SiliconFlow 的 API 调用。**后来 Rerank 改为本地模型，减少了这个依赖。**

------

## 6. 连线关系（谁调谁）





```
浏览器 → 前端 → API路由 → S1 ChatService
                              ↓ 同时调用
                S2 S3 S4 S5 S6 S7（各专业服务）
                              ↓ 各自访问
                MySQL / Redis / Milvus / Neo4j / Cloud
```

# 二、聊天请求处理流程（用户发一条消息发生了什么）

这是**最核心的流程**，共 10 个步骤：

```
用户提问
  ↓
Step 1：JWT 鉴权
  ↓
Step 2：屏蔽词检测
  ↓
Step 3：加载记忆（Redis 最近 20 轮）
  ↓
Step 4：Query 改写 — 用 LLM 改写问题
  ↓
Step 5：混合检索（4 个子步骤）
  ├── BM25 关键词检索（权重 0.4）
  ├── ANN 向量检索（权重 0.6）
  ├── 融合去重
  └── Rerank 精排（bge-reranker-v2-m3）
  ↓
Step 6：图谱增强（Neo4j / LightRAG 补充关系）
  ↓
Step 7：构建 Prompt（人设 + 检索上下文 + 记忆）
  ↓
Step 8：LLM 流式生成（DeepSeek-V3）
  ↓
Step 9：SSE 推送前端（边生成边显示）
  ↓
Step 10：持久化（写 MySQL + 更新 Redis）
```

### 逐步细讲：

**Step 1 — JWT 鉴权**：验证请求里的 Token 是否合法，是否过期。没通过就直接返回 401，不往下走。

**Step 2 — 屏蔽词检测**：过滤违规内容，防止用户输入有害词汇。

**Step 3 — 加载记忆**：从 Redis 取出这个用户、这个角色、这次会话的最近 20 轮对话。这是实现「多轮对话」的关键。

**Step 4 — Query Rewrite（问题改写）**：把用户的问题 + 历史对话一起喂给 LLM，让 LLM 生成一个「补全了所有指代的完整问题」。例如：

> 历史：问了"武汉兴图的主营业务"
> 用户说："它的净利润呢？"
> 改写后：**"武汉兴图新科电子股份有限公司的净利润是多少？"**

改写后的问题才去做检索，效果更准。

**Step 5 — 混合检索**（最复杂的一步）：

- **BM25**：关键词精确匹配，权重 0.4，搜"武汉兴图"、"净利润"这类精确词效果好
- **ANN（向量检索）**：把问题转成向量，在 Milvus 里找距离最近的段落，权重 0.6，搜同义词效果好
- **融合去重**：两路结果合并，相同段落去重，按加权分数排序
- **Rerank 精排**：用 `bge-reranker-v2-m3` 模型对所有候选段落重新打分，这个模型专门训练来判断「这段话能不能回答这个问题」，精度更高

**Step 6 — 图谱增强**：查 Neo4j 或 LightRAG，补充「公司-股东-关联方」等结构化关系。普通文字搜索覆盖不了多跳关系（如"A 的股东的关联公司的法人是谁"），图谱可以。

**Step 7 — 构建 Prompt**：把三样东西拼在一起：

1. 角色人设（这个角色的性格、领域、说话方式）
2. 检索到的上下文段落（来自 PDF）
3. 最近的历史记忆（来自 Redis）

组成完整的输入交给大模型。

**Step 8 — LLM 流式生成**：DeepSeek-V3 逐 token 生成回答。

**Step 9 — SSE 推送**：每生成几个字就立刻推给前端，用户看到的就是逐字出现的效果。

**Step 10 — 持久化**：整条消息写入 MySQL（永久存档），同时更新 Redis 里的短期记忆（加入这一轮）。

# 三、知识入库流程（上传 PDF 发生了什么）





```
PDF 上传
  ↓
PyPDF2 解析（提取文字）
  ↓
固定分块（每块 800 字，120 字重叠）
  ↓           ↓
Embedding   jieba 分词
向量化       BM25 索引
  ↓           ↓
       写入 Milvus
  （按 character_id 隔离，COSINE 度量）
```

​	关键参数：

- **800 字 / 块**：每个片段大约这么长，太长 LLM 处理不了，太短信息不完整。
- **120 字重叠**：相邻两块有 120 字是一样的，防止一句话正好被切断导致语义断裂。
- **bge-large-zh 1024维**：每个文本块被转成一个 1024 个数字的向量，代表语义。
- **character_id 隔离**：每个角色的知识存在单独的命名空间里，不同角色互不干扰。

# 四、服务依赖关系图





```
ChatService（总调度）
    ├── LLMService（大模型）
    ├── PDFIngestService（检索）← 也依赖 LLMService（Query Rewrite）
    ├── MemoryService（记忆）
    ├── GraphService（图谱）← 也依赖 LLMService（实体抽取）
    ├── LightRAGService
    └── ContextService（环境信息）
```

注意两个二级依赖：

- 

  PDFIngestService

   自己也调 

  ```
  LLMService
  ```

  （做

   Query Rewrite）

  

- `GraphService` 自己也调 `LLMService`（提取实体、做图谱问答）

所以 `LLMService` 实际上是**被所有人都依赖的公共组件**。

# 五、技术栈一览（答辩时最常被问的）

| 你被问到                            | 回答要点                                                     |
| :---------------------------------- | :----------------------------------------------------------- |
| 为什么用 FastAPI                    | 因为它天生支持异步，做那种一个字一个字往外蹦的流式回复特别方便，不用折腾。而且自带 API 文档，省事。 |
| 为什么用 Milvus                     | 它就是专门干向量检索的，找相似内容特别快。而且它能同时支持用 BM25 做关键词过滤，一个库里搞定两种搜索。 |
| 为什么用 Neo4j                      | 这个是图数据库，查那种多层关系（比如“朋友的朋友的朋友”）比 MySQL 来回 JOIN 快得多。 |
| 为什么用 Redis                      | 内存级的速度，存最近 20 轮聊天记录这种高频读写的临时数据，读写飞快，重启就没了也没关系。 |
| 为什么 Embedding 用 bge-large-zh    | 专门为中文优化的模型，1024 维向量表达能力够用，而且 SiliconFlow 上有现成的 API 可以直接调。 |
| 为什么 Rerank 用 bge-reranker-v2-m3 | 因为它**准、懂中文、大小合适、有现成接口**，用在这套流程的最后一步做精排最合适。 |
| DeepSeek-V3 是什么                  | 国内开源大模型里的顶流，推理能力强，我们不走本地部署，直接调 SiliconFlow 的 API，接口跟 OpenAI 格式一样，很省心。 |

------

**一句话总结整个架构**：
用户发消息 → JWT 验证 → 改写问题 → 三路搜索文件（关键词+向量+图谱）→ 精排 → 拼接人设和记忆给大模型 → 逐字流式返回 → 存档。
