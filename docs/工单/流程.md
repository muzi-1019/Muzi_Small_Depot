# 一、系统整体是怎么跑起来的？

你的项目是一个 **FastAPI 后端 + RAG 检索 + 大模型生成 + Redis 记忆 + Milvus 向量库 + Neo4j 图谱** 的角色问答系统。

整体流程可以概括成：

```
用户请求
  ↓
FastAPI 路由
  ↓
依赖注入创建 Service / Repository
  ↓
ChatService 编排聊天流程
  ↓
MemoryService 读取对话记忆
  ↓
PDFIngestService 做 RAG 检索
  ↓
LLMService 组织 Prompt
  ↓
LLMClient 调用大模型接口
  ↓
返回普通响应或流式响应
```

你的代码里主要分成这些层：

| 层级            | 代码位置                           | 作用                                                        |
| :-------------- | :--------------------------------- | :---------------------------------------------------------- |
| 应用入口层      | app/main.py                        | 创建 FastAPI 应用、注册中间件、注册路由、启动时初始化数据库 |
| 配置层          | app/core/config.py                 | 管理数据库、Redis、Milvus、Neo4j、大模型、RAG 参数          |
| 依赖注入层      | app/core/deps.py                   | 给 API 自动注入数据库、Repository、Service、鉴权信息        |
| 业务编排层      | app/services/chat_service.py       | 编排完整聊天流程                                            |

| 大模型服务层    | app/services/llm_service.py        | 组织 Prompt、生成回答、流式输出、摘要、Query Rewrite        |

```python
def get_current_user_id(credentials: HTTPAuthorizationCredentials = Depends(security)) -> int:
    token = credentials.credentials
    try:
        payload = jwt.decode(token, settings.jwt_secret, algorithms=[settings.jwt_algorithm])
        user_id: str = payload.get("sub")
        if user_id is None:
            raise HTTPException(...)
```

实现过程：

实现思路：

- Token 无效或过期就返回 `401`。

## 流式聊天实现过程

代码位置：

```python
def send_message_stream(...)
```

核心逻辑：

```python
for chunk in self.llm_service.generate_stream(
    character=character,
    question=llm_question,
    context=context,
    memory=memory,
    realtime_context=realtime_ctx
):
    chunk_count += 1
    full_answer_parts.append(chunk)

```

实现过程：

```
前面的用户校验、记忆、RAG 检索都一样
↓
调用 LLMService.generate_stream()
↓
大模型每返回一段 chunk
↓
后端立刻 yield 给前端
↓
前端实现打字机效果
↓
流式结束后，把完整回答拼起来保存到数据库
```

设计思路：

- 普通接口：等模型完整回答后一次返回。
- 流式接口：模型生成一点就返回一点，用户体验更好。
- 但数据库保存的仍然是完整答案，不保存碎片。

# 六、Query Rewrite 是怎么实现的？

## 代码位置

app/services/llm_service.py

关键代码：

```python
def rewrite_query(question: str, memory: str) -> str:
```

实现逻辑：

```python
if not memory or not memory.strip():
    return question
```

如果没有历史记忆，不改写。

然后：

```python
provider = (settings.llm_provider or "mock").lower()
if provider not in {"openai", "vllm", "sglang", "siliconflow", "silicon_flow", "silicon-flow"}:
    return question
```

如果不是真实大模型，也不改写。

然后构造 Prompt：

```python
messages = [
    {"role": "system", "content": (
        "你是一个 Query Rewriting 助手。根据对话历史，将用户最新的问题改写为一个独立、完整、适合检索的查询。\n"
        "规则：\n"
        "1. 解析指代词（他/她/它/这个公司/该产品等）替换为具体实体名称\n"
        "2. 补全省略的主语或上下文\n"
        "3. 如果问题已经足够清晰，直接返回原问题\n"
        "4. 只返回改写后的问题，不要解释"
    )},
    {"role": "user", "content": f"对话历史：\n{memory[-1500:]}\n\n用户最新问题：{question}\n\n改写后的检索查询："},
]
```

再调用：

```python
data = LLMClient.chat(messages, temperature=0.1, max_tokens=150, timeout=10.0)
rewritten = LLMClient.extract_message_content(data)
```

## 实现过程

```
当前问题 + 最近对话记忆
↓
交给大模型判断是否有指代词
↓
如果有“它、这个公司、他”等模糊表达
↓
改写成完整问题
↓
用改写后的问题去检索
```

例如：

```
Q1：武汉兴图新科的主营业务是什么？
Q2：它的营收是多少？
```

会改写为：

```
武汉兴图新科的营收是多少？
```

## 设计思路

RAG 检索不能直接拿模糊问题去搜。
因为 Milvus / BM25 不知道“它”是谁。

所以先 Query Rewrite，再检索，能提升多轮问答的准确性。

## 会话记忆 Key

代码：

```python
def _session_key(user_id: int, character_id: int, conversation_id: int | None = None) -> str:
    if conversation_id:
        return f"chat:session:{user_id}:{character_id}:{conversation_id}"
    return f"chat:session:{user_id}:{character_id}"
```

实现了：


# 九、Hybrid 混合检索是怎么实现的？

## 代码位置

app/services/pdf_ingest_service.py

核心函数：

```python
def search_hybrid(self, character_id: int, query: str, top_k: int | None = None) -> list[dict[str, object]]:
```

这个函数是你 RAG 的核心。

------

## 整体流程

代码注释里写得很完整：

```
用户问题
  ↓
Query Rewrite
  ↓
同时执行三路检索
  ├─ BM25 关键词检索
  ├─ 向量检索 ANN
  └─ Neo4j 图谱检索
  ↓
三路结果合并去重
  ↓
按 0.4 BM25 + 0.6 向量加权融合
  ↓
取候选结果
  ↓
Rerank 精排
  ↓
返回 Top-K 给大模型
```

------

## 并发执行三路召回

代码：

```python
from concurrent.futures import ThreadPoolExecutor
```

然后：

```python
with ThreadPoolExecutor(max_workers=3) as pool:
    kw_future = pool.submit(self.search_keyword, character_id, query, max(top_k, 8))
    vec_future = pool.submit(self.search_vector, character_id, query, max(top_k, 8))
    neo4j_future = pool.submit(Neo4jGraphService().search_rows, character_id, query,max(top_k, settings.neo4j_top_k))
```

实现过程：

```
开 3 个线程
↓
线程 1 跑 BM25
线程 2 跑 Milvus 向量检索
线程 3 跑 Neo4j 图谱检索
↓
三路并发执行
```

设计思路：

三路检索互不依赖。
如果串行执行：

```python
BM25 200ms + Milvus 300ms + Neo4j 300ms = 800ms
```

并行后可能接近：

```python
max(200ms, 300ms, 300ms) = 300ms
```

所以并发能降低检索延迟。

------

## 单路异常隔离

代码：

```python
kw_rows = self._safe_retrieval_result(kw_future, "keyword")
vec_rows = self._safe_retrieval_result(vec_future, "vector")
neo4j_rows = self._safe_retrieval_result(neo4j_future, "neo4j")
```

具体实现：

```python
@staticmethod
def _safe_retrieval_result(future, name: str) -> list[dict[str, object]]:
    try:
        rows = future.result()
        return rows if isinstance(rows, list) else []
    except Exception as exc:
        logger.warning("[Hybrid] %s retrieval failed: %s", name, exc, exc_info=True)
        return []
```

实现了什么？

```
如果 BM25 出错 → 返回 []
如果 Milvus 出错 → 返回 []
如果 Neo4j 出错 → 返回 []
```

但不会让整个检索失败。

设计思路：

RAG 系统要保证可用性。
三路召回是增强能力，不应该让其中一路故障拖垮整个问答。

例如：

```
Milvus 暂时不可用
↓
系统还能用 BM25 + Neo4j 回答
 
Neo4j 不可用
↓
系统还能用 BM25 + Milvus 回答
```

这是你最近优化的重点之一。

------

## BM25 结果融合

代码：

```python
for row in kw_rows:
    text = str(row.get("text", ""))
    if not text:
        continue
    merged[text] = {
        **row,
        "vector_score": 0.0,
        "keyword_score": float(row.get("score", 0.0)),
        "hybrid_score": float(row.get("score", 0.0)) * settings.hybrid_keyword_weight,
    }
```

实现了：

```
遍历 BM25 结果
↓
以 text 作为去重 key
↓
保存 keyword_score
↓
hybrid_score = BM25 分数 × 关键词权重
```

当前配置里：

```python
hybrid_keyword_weight = 0.4
```

所以 BM25 分数按 0.4 权重参与融合。

------

## 向量结果归一化和融合

代码：

```python
vec_scores = [float(r.get("score", 0.0)) for r in vec_rows]
min_vec = min(vec_scores) if vec_scores else 0.0
max_vec = max(vec_scores) if vec_scores else 0.0
```

然后：

```python

```

实现了：

```
收集向量分数
↓
计算 min / max
↓
把向量分数归一化到 0~1
```

为什么要归一化？

因为向量分数和 BM25 分数不是一个量纲。
向量可能是相似度，BM25 是词频统计分。
直接相加不合理，所以向量分数先标准化。

融合代码：

```python
existing["hybrid_score"] = float(existing.get("hybrid_score", 0.0)) + normalized_vec * settings.hybrid_vector_weight
```

当前配置：

```python
hybrid_vector_weight = 0.6
```

所以：

```
最终向量贡献 = 归一化向量分数 × 0.6
```

如果某条文本同时被 BM25 和向量命中：

```python
existing["method"] = "hybrid"
```

表示它是混合命中，更可信。

## Neo4j 图谱结果融合

代码：


实现思路：


这些关系型问题，单靠文本 chunk 不一定稳定。

## 候选池扩大

代码：


# 十、Rerank 精排是怎么实现的？

## 代码位置

app/services/pdf_ingest_service.py

函数：

```python
def _rerank(self, query: str, rows: list[dict[str, object]], top_n: int | None = None) -> list[dict[str, object]]:
```

注释：

```python
"""调用 SiliconFlow rerank API 对候选文档重新精排。
失败时静默回退到混合检索分数排序，不阻塞主流程。
"""
```

## 实现思路

第一阶段 Hybrid 检索是“召回”：

```
宁可多找一些相关候选
不要漏掉答案
```

第二阶段 Rerank 是“精排”：

```
让模型判断 query 和每个候选 chunk 的真实相关性
```

为什么需要 Rerank？

因为：

- BM25 可能只因为关键词相同而命中。
- 向量可能语义相似但事实不对。
- Neo4j 可能补充了关系，但不一定正好回答问题。

Rerank 可以更精细地判断：

```
这个片段到底能不能回答这个问题？
```

失败时：

```python
return rows[:top_n]
```

也就是不阻塞主流程。

# 十五、答辩时可以怎么讲实现过程？

你可以这样说：

> 我的系统不是直接把用户问题丢给大模型，而是先通过 ChatService 做统一编排。用户请求进入 FastAPI 后，依赖注入层会创建 ChatService、Repository 和 MemoryService。ChatService 先校验用户和角色，再从 Redis 中读取最近对话记忆。如果开启 Query Rewrite，就调用 LLMService 根据历史上下文把模糊问题改写成独立查询。之后进入 PDFIngestService 的 Hybrid 检索流程，并行执行 BM25、Milvus 向量检索和 Neo4j 图谱检索。三路结果会做异常隔离、去重、加权融合，再经过 Rerank 精排得到 Top-K 上下文。最后 LLMService 把角色人设、知识片段、记忆、实时上下文和用户问题组装成 OpenAI 格式 messages，通过 LLMClient 统一调用大模型接口，返回普通答案或流式答案。

# 十七、一句话总结

你的代码实现思路是：

> 用 `ChatService` 作为总编排层，把用户问题、角色信息、对话记忆、RAG 检索结果和实时上下文统一组织起来；用 PDFIngestService 完成 PDF 知识入库和BM25 + Milvus \+ Neo4j 的混合检索；用 MemoryService 管理 Redis 短期记忆；用 LLMService 负责 Prompt 组织和 Query Rewrite；最后通过 LLMClient 统一调用 OpenAI 兼容大模型接口，支持普通回答和流式回答。整体设计重点是：知识可检索、回答有依据、多轮能记忆、检索能降级、模型调用统一封装。
