为什么做这个系统

一句话概括：

# 二、按工单阶段讲项目

## 1. 基础 PDF 问答阶段

最开始的目标是把基础 RAG 跑通。

也就是：

```
PDF 上传
→ PDF 文本解析
→ 文本切分
→ Embedding 向量化
→ 写入 Milvus
→ 用户提问
→ 向量检索
→ 大模型回答
```

> 第一阶段我先搭建基础 RAG 闭环，让系统能够基于上传的 PDF 文档回答问题。这个阶段的重点是打通“文档入库”和“问题检索”两条主链路。

项目里对应：

- **`KnowledgeService`**：处理文件上传。
- **`PDFIngestService`**：处理 PDF 解析、切分、向量化、入库、检索。
- **`ChatService`**：处理用户聊天流程。
- **`LLMService`**：负责编排大模型生成、流式输出、摘要和 Query Rewrite。
- **`LLMClient`**：统一封装 OpenAI 兼容接口的 HTTP 调用、流式调用和响应解析。

------

## 2. PDF 解析优化阶段

普通 PDF 只提取文本是不够的，尤其是金融类 PDF。

招股说明书里有很多：

- **正文段落**
- **财务表格**
- **扫描页**
- **图片**
- **流程图**
- **股权结构图**
- **组织结构图**

所以我项目的 `pdf_ingest_service.py` 做了复杂 PDF 解析。

整体逻辑：

```
PDF 页面
├── 文本层提取
├── OCR 扫描件识别
├── 表格解析并转 Markdown
└── 图片抽取并调用视觉模型描述
```

> 第二阶段我重点优化了 PDF 解析能力。因为金融文档不是纯文本，里面有表格、扫描页、图片和图表。如果只做普通文本抽取，会丢失很多关键信息。所以我把文本、OCR、表格、图片描述统一转成可检索文本，再进入后续 chunk 和 embedding 流程。

------

## 3. 表格解析阶段

我的项目当前做法是：

```
page.find_tables()
→ table.extract()
→ 二维数组
→ Markdown 表格
→ 合并到页面文本
→ 后续切分、向量化、入库
```

为什么要转 Markdown？

因为普通文本可能会把表格打乱。

例如原表格是：

| 年份 | 营业收入 | 净利润  |
| :--- | :------- | :------ |
| 2022 | 1 亿     | 2000 万 |

如果直接抽文本，可能变成：

```
年份 营业收入 净利润 2022 1亿 2000万
```

模型不一定知道哪个数对应哪个字段。

Markdown 可以保留：

```
| 年份 | 营业收入 | 净利润 |
| --- | --- | --- |
| 2022 | 1亿 | 2000万 |
```

> 表格解析的核心不是把单元格文字提出来，而是尽量保留行列关系。当前项目把表格转成 Markdown，是因为 Markdown 既能保留表头、行、列结构，又能直接进入现有的文本向量化和 RAG 管道。

------

## 4. 图像解析阶段

PDF 里有些图片是有价值的，比如：

- **流程图**
- **组织结构图**
- **股权结构图**
- **数据趋势图**
- **业务架构图**

这些图片不能简单丢掉。

当前我的项目做法：

```text
PDF 页面
→ 提取图片
→ 过滤小图 / Logo
→ Base64 编码
→ 调用视觉模型
→ 得到中文描述
→ 追加到页面文本
```

> 图像解析的目标是把图片变成可检索的文本。对于流程图、结构图、趋势图这种有语义价值的图片，我会调用多模态模型识别图片内容，把它转成中文描述，再进入 RAG 知识库。

------

## 5. 检索优化阶段

最开始是纯向量检索。

但纯向量检索有问题：

- 对同义表达好。
- 对金额、年份、公司名、股权比例这种精确事实不稳定。

所以项目用了 混合检索。

```
用户问题
├── BM25 关键词检索
├── Milvus 向量检索
└── Neo4j 图谱检索
      ↓
单路异常隔离
      ↓
融合排序
      ↓
Rerank 精排
      ↓
返回 Top-K 上下文
```

> 金融问答既需要语义理解，也需要精确匹配。向量检索解决自然语言语义相似，BM25 解决公司名、年份、金额、比例等精确词面匹配，Neo4j 补充实体关系。三路召回并行执行，并且做了单路异常隔离：如果 Milvus、BM25 或 Neo4j 某一路临时失败，系统会记录日志并降级为空结果，不影响其他召回链路。最后通过 Rerank 对候选结果重新排序，提高上下文质量。

------

## 6. Graph + RAG 阶段

Graph RAG 主要解决关系型问题。

比如：

```
谁控股谁？
A 和 B 有什么关系？
某公司有哪些关联方？
股东之间的持股链路是什么？
```

普通文本 RAG 是从 chunk 中找答案。

Graph RAG 是从实体关系中找答案。

> 对金融问答来说，很多问题不是单个文本片段能解决的，而是实体之间的结构化关系问题。因此我引入 Neo4j，将股东、公司、关联方、控制关系等抽成图谱，再和文本 RAG 一起参与检索。

------

## 7. 测试和性能优化阶段

最后阶段要讲你不是只做功能，还做评估。

质量评估看：

- **关键词命中率**
- **上下文相关性**
- **回答忠实度**
- **回答相关性**
- **RAG 和纯 LLM 对比**

性能评估看：

- **检索耗时**
- **Embedding 耗时**
- **Milvus 查询耗时**
- **Rerank 耗时**
- **LLM 生成耗时**
- **QPS 并发能力**
- **单路检索失败时的降级能力**



> 我把测试分为质量测试、性能测试和稳定性测试。质量上看检索结果是否包含标准答案、回答是否忠实于上下文；性能上分析检索、Rerank 和 LLM 生成各阶段耗时，并通过 QPS 脚本测试并发能力；稳定性上验证某一路检索服务异常时，系统是否能自动降级并继续返回可用结果。

# 1. 多轮对话，如果上个问题是多实体，怎么判断下一个问题的实体？

## 问题本质

这是：

```
多轮对话 + 指代消解 + 实体消歧
```

比如：

```
Q1：赛克赛斯和济南赛明之间是什么关系？
Q2：它的持股比例是多少？
```

这里“它”到底指谁？

可能是：

- **赛克赛斯**
- **济南赛明**
- **上一轮答案里的某个公司**

> 多轮对话中，如果上一轮出现多个实体，我不会直接让大模型强行猜。系统会先从上一轮问题、上一轮答案和当前问题中抽取候选实体，再结合当前问题的谓词判断，比如“持股比例”“控制关系”“注册地址”等。如果只有一个高置信实体，就自动改写问题；如果多个实体置信度接近，就把选择权交给用户，让用户确认具体问的是哪个实体。

## 当前项目流程

```
当前问题
+ 对话历史
+ 上一轮检索来源
        ↓
实体抽取
        ↓
候选实体排序
        ↓
置信度判断
        ↓
高置信：自动 Query Rewrite
低置信：让用户选择
```

## 项目里怎么对应

我项目里已经有基础：

- **`MemoryService`**：保存短期对话记忆。
- **`ChatService`**：每轮问答都会读取 memory。
- **`LLMService.rewrite_query()`**：可以进行问题改写。

> 当前项目已经有记忆和 Query Rewrite 基础，后续可以在 Query Rewrite 前增加实体消歧模块。当模型无法精确判断时，就通过前端弹出候选实体选项。

# 2. 跨页表格怎么判断是同一个表格，并拼接？

## 问题本质

PDF 不是 HTML。

HTML 表格天然是：

```
<tr>
  <td></td>
</tr>
```

但是 PDF 是页面坐标系统，它本质上是：

```
文字 + 坐标 + 线条 + 页面布局
```

所以 PDF 表格解析要恢复：

- **行**
- **列**
- **单元格**
- **表头**
- **单元格坐标**
- **跨页连续关系**

## 当前项目做了什么

当前项目是：

```
page.find_tables()
→ table.extract()
→ 二维数组
→ Markdown 表格
```

已经解决了基础行列关系保存。

## 跨页怎么判断？

跨页表格可以用 5 个条件判断：

- **表头相似**
  - 下一页表头和上一页表头一致。
  - 或者下一页没有表头，但列数一致。
- **列数一致**
  - 上一页 6 列，下一页也 6 列。
- **列宽 / 坐标接近**
  - 每列 x 坐标边界差不多。
- **位置连续**
  - 上一页表格靠近页底。
  - 下一页表格靠近页顶。
- **语义标识**
  - 出现“续表”“接上表”等文字。



> PDF 表格不像 HTML 天然有 `<tr><td>` 结构，所以解析时要根据文字坐标和表格线恢复单元格关系。对于跨页表格，我会根据表头相似度、列数、列宽坐标、页底页顶位置以及“续表”标识判断是否属于同一个表。如果判断为连续表格，就把下一页表格的 rows 追加到上一页表格中，并保持 Markdown 或结构化 table 格式。

## 后续优化方案

```
TableBlock {
  table_id
  page_start
  page_end
  headers
  rows
  column_positions
}
```

然后：

```
当前页表格
→ 和上一页最后一个表格比较
→ 如果连续：合并 rows
→ 如果不连续：新建 table_id
```

# 3. 图像异步：API 图像解析容易堵塞，怎么办？

## 问题本质

图像解析调用多模态 API，耗时高。

如果同步做：

```
PDF 上传
→ 文本解析
→ 表格解析
→ 图片解析 API
→ 等待 API 返回
→ 入库完成
```

会导致整个入库卡住。

## 推荐方案

拆成两条链路：

```
主链路：
PDF 文本 / 表格 / OCR 快速入库
 
异步链路：
图片抽取
→ 保存图片路径和元数据
→ 投递任务队列
→ 独立图像解析服务
→ 回写图片描述
→ 更新向量库
```

> 图像解析我会从 PDF 入库主流程里拆出去。主流程只负责抽取图片、保存图片路径、页码和附近文本，然后把图片解析任务放入队列。单独启动图像解析服务调用多模态 API，解析完成后把图片描述回写到知识库。这样既不会阻塞 PDF 文本入库，又能保证图片内容后续逐步补全。

## 怎么保证连贯性？

保存元数据：

```
document_id
page_no
image_index
image_path
nearby_text
caption
status
```

这样图片描述回来后，知道它属于哪个 PDF、哪一页、哪个上下文。

# 4. 各阶段方案对比，怎么突出技术亮点？

答辩时不要只说“我用了什么技术”。

要按这个结构讲：

```
遇到什么问题
→ 对比了什么方案
→ 为什么选当前方案
→ 解决了什么场景
```

## 举例 1：PDF 文本解析

- **问题**
  - PDF 中有文本、表格、图片、扫描页。
- **方案对比**
  - 只抽文本：简单，但信息丢失。
  - OCR 全页识别：覆盖广，但慢。
  - 多路解析：复杂，但效果最好。
- **最终方案**
  - 文本层优先，低文本页才 OCR，表格和图片单独处理。
- **解决问题**
  - 兼顾速度和信息完整性。

## 举例 2：检索方案

- **问题**
  - 纯向量检索对数字和公司名不稳定。
- **方案对比**
  - 纯向量：语义好，事实精确弱。
  - BM25：精确好，语义弱。
  - 混合：两者结合。
- **最终方案**
  - BM25 + Vector(向量) + Neo4j -> Rerank
- **解决问题**
  - 同时覆盖语义问题和金融事实问题。
  - 单路召回异常时自动降级，不影响整体问答流程。

## 举例 3：图像处理

- **问题**
  - PDF 里的图表无法检索。
- **方案对比**
  - 直接丢弃：快，但丢信息。
  - OCR 图片：只能识别文字。
  - 多模态模型：能理解图表结构和语义。
- **最终方案**
  - 有价值图片调用多模态模型，装饰图只保存资源路径。

# 5. 图片资源怎么分类处理？

可以分三类讲。

## 第一类：有搜索价值的图片

例如：

- **流程图**
- **组织结构图**
- **股权结构图**
- **数据趋势图**

处理方式：

```
图片抽取
→ 多模态模型识别
→ 生成文本描述
→ 入库检索
```

> 对于流程图、结构图这类有语义价值的图片，我会调用多模态模型识别其中的节点、连线、层级和相对位置，把图片转成可检索文本。

------

## 第二类：有展示价值但搜索价值弱的图片

例如：

- **Logo**
- **封面图**
- **宣传图**
- **装饰图**

处理方式：

```
保存图片路径
→ 不进入向量检索
→ 用户命中文档时作为附件展示
```



> 有些图片没有检索价值，但有展示价值。比如封面图、Logo，我会保存图片路径和页码，当用户检索到相关内容时，可以把图片作为资源返回给前端展示或下载。

------

## 第三类：多模态 RAG 拓展资源

后续可以做：

```
文本向量库
+ 图片向量库
+ 表格结构库
+ 图谱库
```



> 后续可以扩展成真正的多模态 RAG，不仅检索文本，也检索图片 embedding、表格结构和图谱关系，实现图文混合检索。

# 6. Query 改写不确定时，怎么把选择权给用户？

## 问题本质

大模型不一定能准确判断用户意图。

尤其是：

```
它是谁？
这个公司呢？
那它的比例是多少？
```

如果历史里有多个实体，就容易错。

> Query Rewrite 不应该在低置信场景下强行改写。当系统发现候选实体有多个，或者模型判断置信度不够时，可以生成几个候选选项交给用户选择。用户选定后，再把问题改写成明确问题进行检索。

## 示例

用户问：

```
它的持股比例是多少？
```

系统提示：

```
你想问的是哪个主体？
A. 赛克赛斯
B. 济南赛明
C. 济南宝赛
```

用户选 A 后，系统改写成：

```
赛克赛斯的持股比例是多少？
```

再进行检索。

# 7. 表格检索技术和实现思路，利弊是什么？

## 方案一：表格转普通文本

优点：

- **实现简单**
- **能复用普通文本 RAG**

缺点：

- **行列关系容易丢失**
- **金额、年份、指标容易错配**

------

## 方案二：表格转 Markdown

这是我项目当前方案。

优点：

- **保留表头、行、列**
- **LLM 容易理解**
- **能直接进入现有向量库**

缺点：

- **跨页表格处理还不完善**
- **合并单元格支持有限**
- **大表格可能 chunk 过长**

------

## 方案三：结构化表格入库

把表格拆成：

```
table_id
row_index
col_index
header
cell_value
page_no
```

优点：

- **支持精确查询**
- **可以做数值比较**
- **可以定位具体单元格**

缺点：

- **实现复杂**
- **需要额外结构化索引**
- **和自然语言 RAG 融合成本高**

## 

> 当前项目采用 Markdown 表格入库，是实现成本和效果之间的折中。它比普通文本更能保留表格结构，又能复用现有 RAG 管道。后续如果要做更精确的金融表格问答，可以进一步把表格拆成结构化单元格，结合 SQL 或结构化索引实现精确查询。

# 四、最后可以这样完整收尾

答辩最后：

> 这个项目是按照 RAG 系统能力逐步增强的思路完成的。第一阶段先跑通基础 PDF 问答；第二阶段针对复杂 PDF 增强文本、OCR、表格和图片解析；第三阶段发现纯向量检索对金融精确信息不稳定，所以引入 BM25、向量和图谱的混合检索；第四阶段针对多实体关系问题引入 Graph RAG；第五阶段通过 Query Rewrite 和多轮记忆优化对话体验；最后通过评估和性能测试验证系统效果。
>
> 项目的核心亮点是 `pdf_ingest_service.py`，它把复杂 PDF 转换成可检索、可追溯、可融合的知识资产。通过 BM25、向量检索、Neo4j 图谱召回和 Rerank 精排，系统既能处理自然语言语义问题，也能处理金融文档中的金额、年份、股权比例、实体关系等精确问题。
