# RAG 工单与答辩问题讲解

## 一、工单主线梳理

这个项目可以按 13 个工单理解成一条逐步增强的 RAG 系统建设路线：

1. **基础 PDF 问答系统**：完成 PDF 文档上传、解析、切分、向量化、检索和问答生成。
2. **PDF 问答优化**：优化文本切分、检索质量、Prompt 构造和回答稳定性。
3. **表格解析及检索优化**：解决招股说明书、财报类文档中表格结构丢失的问题。
4. **图像内容解析及检索优化**：解决 PDF 中图表、流程图、结构图、截图等非文本信息无法检索的问题。
5. **Query 理解优化**：解决多轮对话、省略指代、问题改写、实体消歧等问题。
6. **混合检索**：将 BM25 关键词检索、向量检索和后续图谱召回结合，提高召回率和准确率。
7. **功能测试及评估**：用标准问题集、RAGAS、命中率、上下文相关性等指标评估效果。
8. **Graph + RAG 金融问答**：引入知识图谱，解决实体关系、股权关系、关联方关系等结构化问题。
9. **Graph + RAG 优化**：从实体抽取、关系构建、图检索、Prompt 等层面提升图谱问答效果。
10. **系统部署**：用 Docker / docker-compose 将系统部署到服务器。
11. **Embedding 模型微调**：解决通用 Embedding 模型在金融专业语义上的“语义鸿沟”。
12. **LightRAG 优化**：用更轻量的图结构和双层检索机制优化传统 RAG 的复杂关系理解能力。
13. **RAG 性能瓶颈识别与优化**：定位 Embedding、Milvus、Rerank、LLM、图谱检索等环节的耗时，优化到可接受延迟。

## 二、项目按阶段怎么讲

### 阶段 1：先实现一个能跑通的基础 RAG

最开始的目标不是追求复杂能力，而是打通主链路：

```text
PDF 上传 → 文本抽取 → 文本切分 → Embedding → Milvus 入库 → 用户提问 → 检索相关片段 → LLM 生成回答
```

项目中对应的核心模块是：

- `KnowledgeService`：负责知识文件上传和入库入口。
- `PDFIngestService`：负责 PDF 解析、切分、向量化、Milvus 入库和检索。
- `ChatService`：负责用户提问后的整体问答编排。
- `LLMService`：负责调用大模型生成回答。

答辩时可以说：

> 第一阶段我先搭建了基础 RAG 闭环，让系统能够基于上传 PDF 进行问答，而不是单纯依赖大模型自身知识。这个阶段重点是跑通“文档入库”和“问答检索”两条链路。

---

### 阶段 2：优化 PDF 解析，解决复杂 PDF 问题

普通 PDF 只提取文本是不够的，招股说明书、财报等金融文档里有大量表格、扫描页、图片和图表。

所以 `pdf_ingest_service.py` 里做了多路解析：

```text
PDF 页面
├── 文本层：page.get_text("text")
├── OCR：扫描页 / 图片页文字识别
├── 表格：find_tables() → Markdown 表格
└── 图片：提取图片 → 视觉模型描述 → 文本化
```

答辩时可以说：

> 这个阶段的技术亮点是把复杂 PDF 中不同形态的信息统一转成可检索文本。文本、表格、OCR 和图片描述最后都会进入同一个 chunk 管道，后续可以统一向量化和检索。

---

### 阶段 3：优化检索，从单一向量检索变成混合检索

单纯向量检索有缺点：语义相似度强，但对金额、年份、公司名、股权比例等精确信息不稳定。

因此项目使用 Hybrid 检索：

```text
用户问题
├── BM25：精确关键词、数字、人名、公司名
├── Vector：语义相似、同义表达、自然语言问题
└── Neo4j：实体关系、股权关系、关联方关系
      ↓
结果融合 → Rerank 精排 → 返回 Top-K 上下文
```

答辩时可以说：

> 金融文档问答既需要语义理解，也需要精确事实匹配。BM25 解决词面和数字精确召回，向量检索解决语义泛化，Neo4j 补充结构化关系，Rerank 再做最终相关性排序。

---

### 阶段 4：多轮对话和 Query 理解优化

多轮对话的关键问题是：用户后续问题经常省略实体。

例如：

```text
Q1：赛克赛斯和济南赛明之间是什么关系？
Q2：它的持股比例是多少？
```

这里“它”到底指赛克赛斯还是济南赛明，就需要实体消歧。

项目当前可以通过：

- 短期记忆 `MemoryService`
- Query Rewrite
- 对话历史拼接
- 必要时让用户选择实体

来解决。

答辩时可以说：

> 对于多轮问题，我不会盲目让大模型强行猜实体。系统会先从上一轮问题、上一轮答案和当前问题中抽取候选实体。如果只有一个高置信实体，就自动补全；如果存在多个候选实体且置信度接近，就把选择权交给用户，让用户确认具体指代对象。

---

### 阶段 5：Graph + RAG 与 LightRAG

传统 RAG 是“文本块检索”，适合从文档里找片段，但对复杂实体关系不够强。

Graph + RAG 解决的是：

- 谁控制谁？
- 谁持股谁？
- 哪些公司有关联关系？
- 多个实体之间有什么链路？

答辩时可以说：

> 对于金融问答，很多问题不是单个文本片段能解决的，而是实体之间的关系问题。因此我引入 Neo4j 图谱检索，把实体关系转换成结构化上下文，和文本 RAG 一起交给大模型。

LightRAG 可以作为后续优化方向：

> LightRAG 的优势是把图结构融入索引和检索过程，用 Local 和 Global 双层检索增强复杂关系理解，同时降低全量更新成本。

---

### 阶段 6：测试、评估和性能优化

评估不能只看“能不能回答”，还要看：

- 检索片段是否包含答案
- 上下文是否相关
- 回答是否忠实于上下文
- 响应时间是否可接受
- 并发下是否稳定

项目中已有：

- `eval_rag.py`
- `eval_comprehensive.py`
- `benchmark_rag.py`
- `qps_test.py`
- `qps_retrieval.py`

答辩时可以说：

> 我把评估分成质量和性能两类。质量上看关键词命中、上下文相关性、忠实度；性能上看检索耗时、LLM 耗时、Rerank 耗时和并发 QPS。

## 三、答辩 7 个问题的推荐回答

### 1. 多轮对话：上个问题是多实体时，怎么判断下一个问题的实体是哪个？

#### 问题本质

这是多轮对话里的**指代消解和实体消歧**问题。

如果上一轮出现多个实体，例如：

```text
Q1：A 公司和 B 公司之间是什么关系？
Q2：它的持股比例是多少？
```

“它”可能指 A，也可能指 B。

#### 答辩回答

可以分三层处理：

1. **规则层**：看当前问题是否出现明确实体名。如果有，直接使用当前实体。
2. **上下文层**：如果当前问题是“它、该公司、上述公司”等指代词，就从上一轮问题和答案里抽取候选实体。
3. **置信度层**：如果只有一个高置信实体，就自动补全；如果多个实体都可能，就让用户选择。

推荐答法：

> 多轮对话中，如果上一轮出现多个实体，我不会直接让模型猜。系统会先从对话历史中抽取候选实体，再结合当前问题的谓词判断，比如“持股比例”更可能指向被持股主体还是持股主体。如果置信度不够，就返回选项让用户确认，例如“你问的是 A 公司还是 B 公司？”。这样可以避免大模型在多实体场景下误判。

#### 可以落到项目上的实现

当前项目已有：

- `MemoryService` 保存短期记忆
- `LLMService.rewrite_query()` 支持问题改写
- `ChatService` 中会在检索前进行 Query Rewrite

后续可以增强为：

```text
对话历史 → 实体抽取 → 候选实体排序 → 置信度判断 → 自动改写或用户选择
```

### 2. 跨页表格合并：怎么判断翻页表格是同一个表格，并拼接在一起？

#### 问题本质

PDF 表格不像 HTML 表格天然有 `<tr><td>` 结构。PDF 本质更像“页面上的文字和坐标”，表格线、单元格、行列关系都需要解析出来。

跨页表格更难，因为第一页结尾和下一页开头可能是同一张表。

#### 答辩回答

判断跨页表格是否属于同一张表，可以结合以下特征：

1. **表头相似度**：下一页表格表头是否和上一页一致，或者下一页没有表头但列数一致。
2. **列数和列宽一致**：两页表格的列数量、列边界坐标是否接近。
3. **页面位置关系**：上一页表格是否接近页底，下一页表格是否接近页顶。
4. **标题 / 续表标识**：是否出现“续表”“接上表”等文本。
5. **语义连续性**：上一页最后一行和下一页第一行是否属于同一指标序列。

推荐答法：

> PDF 表格解析时我不是直接把文本顺序拼起来，而是先恢复表格的行列结构。对于跨页表格，我会根据表头相似度、列数、列宽坐标、页底页顶位置和“续表”标识判断是否是同一张表。如果判断为同一张表，就将下一页的行追加到上一页表格中，并保持 Markdown 或 HTML table 结构。

#### 项目当前实现

当前项目已实现：

```text
page.find_tables() → table.extract() → Markdown 表格
```

也就是已经保留了基本的二维行列关系。

当前不足：

- 还没有做跨页表格合并
- 还没有保存页码范围和表格 ID
- 对复杂合并单元格支持有限

后续优化方案：

```text
每页表格解析 → 生成 TableBlock → 判断是否和上一页连续 → 合并 rows → 写入 chunk
```

### 3. 图像异步：API 图像解析容易阻塞，怎么优化？

#### 问题本质

图像解析通常要调用多模态模型 API，耗时比文本解析更长。如果在 PDF 入库主流程里同步处理所有图片，会导致上传和入库阻塞。

#### 答辩回答

推荐分成两条链路：

```text
主链路：PDF 文本 / 表格 / OCR 快速入库
异步链路：图片抽取 → 图片任务队列 → 独立图像解析服务 → 回写图片描述
```

推荐答法：

> 图像解析我会从主入库流程里拆出来。主流程只负责抽取图片、保存图片路径和元数据，然后把图片解析任务放到队列里。单独启动图像解析服务调用多模态 API，解析完成后把图片描述回写到知识库。这样不会因为图像 API 慢而阻塞 PDF 入库，同时还能保证后续检索时图片内容逐步补全。

#### 连贯性怎么保证

可以保存这些信息：

- `document_id`
- `page_no`
- `image_index`
- `image_path`
- `nearby_text`
- `caption`
- `status`

这样图片描述回写后，可以和原始页面上下文关联。

### 4. 项目各阶段不同方案怎么对比，怎么突出技术亮点？

#### 答辩思路

不要只说“我用了某个技术”，而要说：

```text
遇到什么问题 → 对比了哪些方案 → 为什么选这个 → 解决了什么场景
```

#### 推荐讲法

1. **基础 RAG 阶段**
   - 问题：大模型无法基于私有 PDF 准确回答。
   - 方案：PDF 解析 + 向量检索 + LLM。
   - 解决：基于文档的问答。

2. **表格阶段**
   - 问题：普通文本抽取会破坏表格行列关系。
   - 方案对比：纯文本抽取 vs Markdown 表格结构化。
   - 选择：Markdown 表格，因为它能保留表头、行列关系，能被 LLM 理解。

3. **图片阶段**
   - 问题：图表、流程图、结构图无法被文本检索。
   - 方案对比：忽略图片 vs OCR 图片文字 vs 多模态模型描述。
   - 选择：对有语义价值的图片调用多模态模型。

4. **检索阶段**
   - 问题：单纯向量检索对数字、年份、公司名不稳定。
   - 方案对比：纯向量 vs BM25 vs Hybrid。
   - 选择：BM25 + Vector + Graph + Rerank。

5. **图谱阶段**
   - 问题：股权、控制、关联关系等需要结构化推理。
   - 方案：Neo4j Graph RAG。
   - 解决：多实体关系类金融问答。

### 5. 图片资源：不同类型图片怎么处理？

图片可以分三类。

#### 第一类：有搜索价值的图片

例如：

- 流程图
- 组织结构图
- 股权结构图
- 数据趋势图
- 业务架构图

处理方式：

```text
图片抽取 → 多模态模型识别 → 生成文本描述 → 入库检索
```

答辩说法：

> 对于流程图、结构图这类有语义价值的图片，我会调用多模态模型识别其中的节点、方向、层级和相对位置，把图片转成可检索文本。

#### 第二类：有展示价值但搜索价值弱的图片

例如：

- 企业 Logo
- 宣传图
- 封面图
- 装饰性图片

处理方式：

```text
保存图片路径 → 不参与向量检索 → 用户命中相关文档时作为附件展示 / 下载
```

答辩说法：

> 有些图片不适合进入检索，比如 Logo 和装饰图，但它们有展示价值。所以我会保存图片路径和页码，当用户检索到相关内容时，可以把图片作为引用资源返回。

#### 第三类：多模态 RAG 拓展资源

例如：

- 图片向量
- 表格向量
- 图像 OCR 结果
- 图文联合 embedding

后续可以做：

```text
文本向量库 + 图片向量库 + 表格结构库 + 图谱库
```

### 6. Query 改写不确定时，怎么把选择权交给用户？

#### 问题本质

大模型不是所有时候都能精确判断用户意图，尤其是多实体、多轮省略、歧义问题。

#### 推荐答法

> 当 Query Rewrite 置信度不够时，不应该强行改写。系统可以生成候选改写或候选实体，让用户选择。比如用户问“它的持股比例是多少”，上一轮出现 A 和 B 两个公司，系统可以提示：“你想问 A 公司的持股比例，还是 B 公司的持股比例？”用户选择后再检索。

#### 实现思路

```text
当前问题 + 对话历史
→ 候选实体抽取
→ 候选 Query 生成
→ 置信度判断
→ 高置信自动改写 / 低置信用户选择
```

前端可以展示：

```text
你想问的是：
A. 赛克赛斯
B. 济南赛明
C. 济南宝赛
```

### 7. 表格检索的技术、实现思路、利弊？

#### 方案一：表格转普通文本

优点：

- 实现简单
- 可以直接进入现有向量库

缺点：

- 行列关系容易丢失
- 年份、金额、指标可能错配

#### 方案二：表格转 Markdown

优点：

- 保留表头、行、列关系
- LLM 容易理解
- 能直接和文本 chunk 一起向量化

缺点：

- 对跨页表格、合并单元格支持有限
- 大表格可能导致 chunk 过长

#### 方案三：结构化表格入库

可以将表格保存为：

```text
table_id
page_no
row_index
col_index
header
cell_value
```

优点：

- 支持精确查询
- 可以做数值比较、列筛选、行定位

缺点：

- 实现复杂
- 需要额外的表格数据库或结构化索引

#### 方案四：表格混合检索

推荐方案：

```text
Markdown 表格文本向量检索 + BM25 精确匹配 + 结构化表格索引
```

答辩说法：

> 当前项目采用 Markdown 表格入库，是在实现成本和效果之间的折中。它比普通文本更能保留行列关系，又能复用现有 RAG 管道。后续如果要支持更精确的金融表格问答，可以进一步把表格拆成结构化单元格，结合 SQL 或结构化检索实现精确查询。

## 四、最终答辩总讲法

可以这样整体讲：

> 我的项目是围绕 RAG 金融问答逐步建设的。第一步先完成基础 PDF 问答，让系统能基于文档回答问题；第二步针对真实 PDF 中的复杂情况，增强了文本、OCR、表格和图片解析；第三步发现单纯向量检索对金额、年份、公司名不够稳定，所以引入 BM25 和 Hybrid 检索；第四步针对金融场景中的实体关系，引入 Neo4j 做 Graph RAG；第五步针对多轮对话，引入记忆和 Query Rewrite，并在歧义场景下让用户确认实体；最后通过评估脚本和性能测试分析系统质量和瓶颈。
>
> 项目的核心亮点是 `pdf_ingest_service.py`，它把复杂 PDF 转换成可检索、可追溯、可融合的知识资产。通过 BM25、向量检索、图谱召回和 Rerank 组合，系统既能处理自然语言语义问题，也能处理金融文档里的精确事实和结构化关系问题。
